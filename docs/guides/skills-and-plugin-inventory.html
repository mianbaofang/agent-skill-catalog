Task guide

Inventory skills and plugins across folders

Once your library outgrows one folder, a flat list stops answering the useful question: is this a standalone Skill, a child of a bigger family, or something a plugin carries? This guide scans several roots into one catalog and shows you how to read the grouping it reports.

Needs Python 3.10+ · Runs from the repository root · Read in Chinese

What you will end up with

One local catalog that covers every root you name, with three distinctions visible instead of flattened:

  • Standalone Skills — self-contained entries, each from its own SKILL.md.
  • Families — one parent entry whose child Skills are listed in the detail view, kept together because they share an observed main entry point.
  • Plugins — Skills supplied by a plugin cache, grouped by provider and plugin name in a separate view, and not counted as standalone Skills.

Step 1: Name each root, and label the plugin cache

The simplest way to scan two roots is to repeat --root. The example below also uses the offline switches from Build an offline skill catalog.

Bash

python skills/agent-skill-catalog/scripts/build_catalog.py \
  --root "/path/to/skills" \
  --root "/path/to/plugin-cache" \
  --output-dir "/path/to/catalog-output" \
  --no-github-discovery \
  --no-github-images

PowerShell

python skills/agent-skill-catalog/scripts/build_catalog.py `
  --root "C:\path\to\skills" `
  --root "C:\path\to\plugin-cache" `
  --output-dir "C:\path\to\catalog-output" `
  --no-github-discovery `
  --no-github-images

For a repeatable setup, use a config file instead, which also lets you label each root as a skill or a plugin and name it. Start from the bundled example for your platform, references/catalog-config.posix.example.json or references/catalog-config.windows.example.json, and pass it with --config:

{
  "roots": [
    {"path": "/path/to/skills", "label": "Skills", "kind": "skill"},
    {"path": "/path/to/plugin-cache", "label": "Plugins", "kind": "plugin"}
  ],
  "output_dir": "/path/to/catalog-output"
}

Expected result. Exit code 0 and a catalog spanning both roots. Entries from the plugin-labeled root appear under the plugin view rather than inflating the standalone count.

Step 2: Read duplicate installs, name collisions, and families

These three situations look similar in a file browser but mean different things. The catalog separates them:

SituationHow the catalog reports it
Verified duplicate installCopies backed by the same observed GitHub repository and the same Skill name collapse to a single entry, and every source location is retained as evidence in the detail view.
Same-name collisionTwo Skills can share a name yet come from unrelated publishers. Without shared repository evidence they stay separate entries rather than being merged.
Parent-child familyNested SKILL.md files group under an observed main entry point and appear as one parent record with its children listed in the detail. Siblings join a family only when their own source description states a clear product-owner or routing relationship; loose keyword mentions stay separate.

Grouping is conservative. When the evidence does not clearly support merging, the catalog keeps entries separate and, for classification uncertainty, marks them for review. A family or duplicate you can see is one the scan could actually support.

Step 3: Keep the inventory read-only

Building an inventory never writes to your roots. Generated JSON, cached previews, and manual image overrides all go to the output directory you chose. Two boundaries are worth stating plainly:

  • No sync, no auto-install, no auto-delete. The catalog reports what it found; it does not reconcile copies across machines, install or remove Skills, or tidy your folders.
  • The optional delete capability belongs to the local server, and is off unless you turn it on. When explicitly enabled for a root via allow_delete, it can permanently remove a top-level standalone Skill directory after you confirm the full Skill name. Family and plugin entries are excluded, and root configuration is not what it deletes. Leave it disabled if you only want to browse.

Troubleshooting

SymptomLikely cause and fix
Plugin cache entries are counted as standalone SkillsThe root was not labeled as a plugin. Pass it with kind: "plugin" in a config file, or check that you pointed --root at the plugin cache rather than mixing it into the Skills root.
Two entries you expected to merge stayed separateThey lack shared repository evidence, or their local content differs. This is intentional: without matching evidence the catalog will not guess that two same-name Skills are the same.
A parent and its children appear as separate entriesThe parent has no observable main entry point, or the children do not declare a relationship. Use an explicit curation override if you want them grouped.
A root is scanned that you did not intendOnly the roots you pass are traversed. Check the --root and --config arguments; the builder does not walk parent folders.
